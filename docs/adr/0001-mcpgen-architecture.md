# 0001. mcpgen — HCL-driven MCP server generator architecture

<!--toc:start-->
<!--toc:end-->

## Status

Accepted

## Context

We have multiple Go services — webhookd, the markdown RFC API, and
more on the roadmap — that would benefit from exposing an MCP
server. Following the patterns in the general Go MCP walkthrough
(`docs/guide/mcp-server-in-go.md`) by hand for each service produces
a predictable amount of boilerplate: config struct, env-var parser,
auth middleware for the chosen scheme, observability spine
(slog + Prometheus + OTel), tool wrappers over business logic or
downstream APIs, `main.go` wiring. Every implementation will look
roughly the same, with the variation concentrated in: which tools
exist, which auth scheme is used, and whether it's a standalone
proxy or mounted inside an existing HTTP service.

We want a generator that collapses that boilerplate into a
declarative spec. The spec needs to:

- Describe the MCP server's identity and tools.
- Pick between two deployment modes: **standalone proxy** (new
  binary that calls a remote API and exposes tool-shaped wrappers)
  and **embed** (add MCP to an existing HTTP service).
- Pick an auth scheme: none, static bearer, OIDC/JWT, or dynamic
  OIDC discovery.
- Point at an API definition (inline or via OpenAPI reference) for
  proxy mode.

Several architectural decisions follow from this and are worth
recording explicitly so later contributors don't re-litigate them.

## Decision

### 1. HCL2 as the configuration language

We use HashiCorp's HCL2 (`github.com/hashicorp/hcl/v2`) for the
input spec. HCL gives us native support for labeled blocks
(which map cleanly to MCP's tool structure), typed attributes,
comments, and an evaluation context that lets specs reference
variables and environment. Struct-tag decoding via `gohcl` keeps
the generator code readable.

### 2. Generator output: text/template + go/format, plus DST for edits

- **New files are generated via `text/template` + `go/format.Source()`.**
  Templates are simple to read, easy to review, and the conventional
  choice for Go codegen (protobuf, stringer, most `go generate`
  tooling). `go/format.Source()` run at write time ensures the
  output is always `gofmt`-clean.
- **Edits to existing files are done with `github.com/dave/dst`
  (Decorated Syntax Tree).** When the "embed" mode needs to modify
  an existing `main.go` to register the MCP handler on an existing
  mux, we edit the AST rather than pattern-matching strings. `dst`
  is chosen over `go/ast` because it preserves comments and
  spacing through round-trip, which `go/ast` does not.

Templates do the 80% — boilerplate, tool stubs, middleware, config.
DST does the 20% — precise edits in unknown-shape existing files.

### 3. Dual input for proxy mode: inline HCL or OpenAPI reference

The proxy mode supports two ways of describing the backend API:

- **Inline:** each tool's backing HTTP call is described directly
  in HCL (method, path, params, response mapping). Useful when the
  target API has no spec (our markdown RFC API, for example).
- **OpenAPI reference:** the HCL points at an OpenAPI 3.x document
  and references operations by `operationId`. Useful when the
  target API already has a spec (Jira, GitHub, internal services
  that publish OpenAPI).

The two paths converge on a common internal model before
generation; the generator itself does not distinguish them past
the parsing stage.

### 4. Dual output: new project or add-to-existing

A CLI flag (`--mode new` vs `--mode embed`) picks between:

- **New project:** generator scaffolds a fresh Go module
  (go.mod, cmd/, internal/, Dockerfile, Makefile) targeted by
  `--out <path>`.
- **Embed:** generator writes into an existing module under a
  subpath (`--out ./internal/mcp`) and performs a minimal edit
  to the designated `main.go` (via DST) to wire up the new
  package.

### 5. Tool name: `mcpgen`

Short, descriptive, matches the convention of `stringer`,
`protoc-gen-go`, etc. Distribution is as a single Go binary; no
runtime dependencies beyond what the generated code needs.

### 6. Observability defaults are non-negotiable

Every generated server ships with slog-to-stdout, Prometheus
metrics, and OpenTelemetry tracing already wired. Users can opt
out via HCL flags (`observability { metrics = false }`), but the
default is on. This follows the "observability spine first"
principle established in the webhookd Phase 1 design: retrofit
costs always exceed up-front cost.

### 7. Generated-code ownership model

Generated files are marked `// Code generated by mcpgen. DO NOT EDIT.`
and are expected to be regenerated, not edited. User business
logic lives in clearly separated hand-written files that the
generator never touches. The generator's edit path (DST-based
`main.go` modification) is the single exception, and it uses
idempotent region markers so regeneration is safe.

## Consequences

### Positive

- **One consistent shape** across every MCP server we ship.
  Reviewers know where auth lives, where metrics are registered,
  where tools get wired up — it's always the same.
- **HCL's expressiveness** handles the config without us inventing
  a DSL. Blocks map to tool definitions cleanly; attributes handle
  options; comments are first-class in the source.
- **Template-based codegen is reviewable.** A new contributor can
  read the templates in a sitting and know what the tool produces.
- **DST over `go/ast`** avoids the well-known pain of losing
  comments and spacing when round-tripping Go source.
- **Two modes cover our realistic needs.** New project for "we
  want a dedicated MCP frontend to $APIs"; embed for "we want to
  add MCP to an existing service."
- **Two proxy-input modes cover our API realities.** OpenAPI when
  the API has a spec, inline HCL when it doesn't.
- **Observability by default** means every generated service shows
  up in Grafana with nothing extra.

### Negative

- **Two codegen technologies** (templates + DST) is more to learn
  than picking one. We accept this because each is genuinely
  better at what it's used for.
- **HCL is less familiar than YAML/JSON** to engineers outside the
  HashiCorp ecosystem. Mitigated by providing an `mcpgen init`
  subcommand that scaffolds a starter config and by strong
  error messages from HCL's diagnostic system.
- **Regeneration safety depends on discipline.** Users who edit
  generated files will lose their edits. The `DO NOT EDIT`
  header is the only enforcement; reviewers need to watch for it.
- **Embed mode's DST edits on `main.go` can be fragile** if the
  target `main.go` is exotic. Mitigated by requiring a specific
  marker comment (`// mcpgen:hook`) that the generator targets;
  if the marker is missing, the generator fails loudly rather
  than guessing.
- **OpenAPI parsing has a non-trivial surface.** We use
  `github.com/pb33f/libopenapi` (actively maintained, 3.x
  compliant) rather than rolling our own. New dependency, but
  the correct tradeoff.

### Neutral

- **Generated code depends on the same libraries the general Go
  MCP walkthrough recommends** (`mark3labs/mcp-go`,
  `prometheus/client_golang`, OTel). Swapping any of them requires
  a template update, but users never touch the imports directly.
- **The generator is a build-time tool.** Run at repo-init time
  or as a `go generate` step in CI; no runtime coupling between
  mcpgen and the services it generates.
- **Config schema evolution** will use a `version` attribute at the
  HCL top level (`mcpgen_version = "1"`); breaking changes bump the
  version and the generator supports the old versions with
  deprecation warnings.

## Alternatives Considered

- **YAML/JSON config instead of HCL.** Simpler, more ubiquitous.
  Rejected because HCL's block labels and expression language are
  a material fit for this problem — we'd end up reinventing pieces
  of them in YAML with less rigor. We already use HCL in other
  Wiz tooling (`fwsync`), so the familiarity cost is low for our
  team.
- **Pure go/ast for everything.** Considered for uniformity.
  Rejected because generating fresh files from AST nodes is
  painful (verbose, easy to produce un-formattable trees), and
  templates are the established idiom. `go/ast` for *analysis*
  remains useful in mcpgen (e.g. verifying that an existing
  `main.go` has the hook marker); we just don't use it for writing.
- **Pure text-replacement edits for embed mode.** Considered for
  simplicity. Rejected because the set of ways a `main.go` can
  legally vary is too large to cover with regex; DST gives us
  structural guarantees at modest additional cost.
- **Generate-via-reflection at runtime** (à la dynamic JSON-RPC
  routing where the config is read at runtime and tools are
  registered reflectively). Rejected because it loses the static
  typing and `gopls` navigation that compile-time generation gives
  us, and because it pushes errors from build time to service
  start time.
- **Cookiecutter-style copy-then-replace templates** (non-Go
  templating, like a directory skeleton with `{{.Name}}` in
  filenames). Rejected because `text/template` in Go is strictly
  more capable (conditionals, ranges) and we already need a Go
  binary for the OpenAPI parsing and DST edits. One technology,
  not two.
- **Single-mode generator (new project only, or embed only).**
  Rejected because we have concrete needs for both and building
  them separately would duplicate the tool/auth/observability
  generation logic.
